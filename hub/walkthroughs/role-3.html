Application developer — requirement, design note, test

Source pointers: G3 §16 · Appendix C §16

Not every-word — S17 first, then G3; deep-read Shall and App C; Should = implement whenever possible.

Reading order: S17, then the same-theme G3 section, then Appendix C only if the system is Tier 2 or Tier 3. Open the source pages for the original wording.

Where a step is Should, you may defer it if you record why. Shall steps are the ones the policy treats as mandatory. App C steps apply when the system is Tier 2 or Tier 3.

  1. Step 1. Pick one change

    A small feature you know. If you use a real backlog item, do not paste secrets or personal data into the note.

    Artefacts to keep: Change name.

  2. Step 2. Write one security requirement

    Tie it to confidentiality, integrity, or availability. “Make it secure” is not a requirement.

    Artefacts to keep: The requirement sentence.

    Shall: security-by-design.

  3. Step 3. Add a design note

    Where the control lives: authentication, authorisation, session, cryptography, or logging. One paragraph.

    Artefacts to keep: The design note.

  4. Step 4. Write a test

    A test that fails if the requirement is absent. Include the negative case, such as a user who should not see the record.

    Artefacts to keep: The test case.

  5. Step 5. Say where secrets go

    Name the secret store. State that the value is not in source.

    Artefacts to keep: The store name.

  6. Step 6. Test data

    State whether the test uses production-like data and how it is protected or anonymised.

    Artefacts to keep: One line on test data.

    Shall when the data is production-like.

  7. Step 7. Tier 2/3 extras

    If the system might be Tier 2 or 3, note shift-left, the pre-production security risk assessment checking design-review follow-ups, and hardening as the production baseline.

    Artefacts to keep: A question for the assessment owner.

    App C Shall once the tier is confirmed.

  8. Step 8. Hand-off

    What operations need from you: log events, and who patches the libraries.

    Artefacts to keep: Two bullets for operations.

Alternative exercise

Alternative: a test-data check. Where did the data come from, is it anonymised, who can read the test store, and when is it deleted?
