    Security in acquisition, development, and maintenance

    Security is a life-cycle requirement. Put it in at initiation and design. Do not leave it as a test you hope to pass at the end.

    Not every-word — S17 first, then G3; deep-read Shall and App C; Should = implement whenever possible.

    Reading order: S17, then the same-theme G3 section, then Appendix C if the system is Tier 2 or Tier 3.

    ShallDEC-SDLC-01

    When do security requirements start?

    At initiation and design, not at the week of go-live. Security-by-design means the requirement is written while the scope can still change.

    Relevance
    Project managers, developers, and the security unit.
    Applicability
    Roles: Application developer, IT security administrator / unit, and Management support.Stages: 01 Project initiation, 02 Design.Tiers: Tier 1, Tier 2, Tier 3.
    Prerequisites
    There is a named change or a new system. “Make it secure” is not yet a requirement.
    Implementation guidance
    Write requirements that name confidentiality, integrity, or availability. Open S17 §16 and G3 §16, and the stage pack for the life-cycle step you are in.
    Source
    S17 §16 G3 §16 S17 §6

    ShallDEC-SDLC-03

    What actions should be taken before system live-run?

    System live-run and production rollout are the same gate. Before that gate, a security risk assessment shall be completed for the information system. If the system involves personal data, a privacy impact assessment shall be completed as well. The same assessments shall be done before a major enhancement or change. A self-assessment checklist does not replace them.

    Relevance
    The security unit and the project team preparing a system for production.
    Applicability
    Roles: IT security administrator / unit and Management support, with System / LAN administrator and Application developer supporting the review.Stages: 06 Go-live, 08 Change.Tiers: Tier 1, Tier 2, Tier 3.
    Prerequisites
    You have a system that is planned to launch in production, and whether it stores or processes personal data.
    Implementation guidance
    Commission the security risk assessment, and the privacy impact assessment where personal data is involved, before system live-run. Use a qualified expert who is independent of the area under review. Agree the scope, method, and report format first, include an on-site inspection and interviews, and keep the assessment record. Put risks that are not yet fully treated into the risk register. Open G3 §20 and S17 §20.
    Source
    S17 §20 G3 §20

    Shall App CDEC-SDLC-04

    Does Appendix C add acquisition controls at Tier 2?

    Yes. Appendix C adds Tier 2 controls on system acquisition and development. Tier 3 inherits them. Confirm the row before you treat a design review as optional.

    Relevance
    Delivery teams for Tier 2 and Tier 3 systems.
    Applicability
    Roles: Application developer and IT security administrator / unit.Stages: 02 Design, 04 Build/Implementation, 05 Testing.Tiers: Tier 2, Tier 3.
    Prerequisites
    The tier is confirmed or explicitly proposed.
    Implementation guidance
    Open the App C matrix at the acquisition row and G3 Appendix C. Keep the baseline §16 work either way.
    Source
    G3 Appendix C S17 §16 G3 §16

    ShouldDEC-SDLC-02

    What should a design note contain?

    Where the control lives: authentication, authorisation, cryptography, logging, or the network path. One clear paragraph beats a slogan.

    Relevance
    Developers and reviewers.
    Applicability
    Roles: Application developer, with IT security administrator / unit reviewing.Stages: 02 Design, 04 Build/Implementation, 05 Testing.Tiers: Tier 1, Tier 2, Tier 3.
    Prerequisites
    A security requirement already exists.
    Implementation guidance
    Tie the note to the requirement and to a test that fails if the control is absent. Keep secrets out of source.
    Source
    S17 §16 G3 §16
